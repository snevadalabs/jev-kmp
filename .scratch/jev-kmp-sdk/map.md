# Map — Jev Kotlin Multiplatform SDK

**Label:** `wayfinder:map`
**Effort:** `jev-kmp-sdk`
**Tracker:** local markdown (`.scratch/jev-kmp-sdk/`) — this folder has no git remote, so there is nothing for `gh` or `glab` to talk to.

## Destination

A published, CI-gated Kotlin Multiplatform SDK for the TypeSafe / Jev System One API — `com.sierranevadalabs:jev-kmp` `0.1.0` on Maven Central, covering JVM + Android + Apple + Linux x64, built on Ktor behind an injectable engine seam, shipping a cross-language wire-conformance fixture suite and an enforced public-API dump, with a test suite that actually gates the release.

## Notes

**Domain.** Jev is TypeSafe's System One model. The API takes a `state` and a map of typed `questions` and returns structured `answers`.

| Primitive | Question | Answer fields |
|---|---|---|
| Noul | is this true? | `noul` (0–1) |
| Choice | pick one option | `choice`, `probabilities`, `confidence` |
| Score | rate on ordered levels | `score`, `legend`, `probabilities`, `confidence` |

Wire: `POST /v1/systemone` `{state, model, questions}` → `{model, answers, usage}`; `GET /v1/models`. All three primitives mix in one call. Answer keys mirror question keys. Errors: `401`, `422`, `429`, `529`; response header `x-typesafe-request-id`.

**Reference material.** Recon of both official SDKs (v0.6.0 each) is in `research/reference-typesafe-sdk-python-recon.md` and `research/reference-typesafe-sdk-js-recon.md`. Live clones of both, plus `system-one-adapter-python`, are at `/tmp/ts-study/`. The TypeSafe docs index is at `https://docs.typesafe.ai/llms.txt`.

**Skills every session should consult.** `tdd` (one runnable check per behaviour, test-first); `codebase-design` (where the seams go — the engine seam is the load-bearing one); `domain-modeling` (write an ADR the moment a hard-to-reverse decision is made); `research` (for tickets typed `research`); `prototype` (for tickets typed `prototype`).

**Execution is in scope.** This effort overrides the wayfinder default of "plan, don't do": tickets resolve a decision *and* land the code it implies. Still **one ticket per session** — research tickets are the only exception and may run in parallel.

**Wayfinding mechanics for this tracker.** A ticket is a file in `issues/`. `Type:`, `Status:` and `Blocked by:` are read from the top of the file. Claim a ticket by setting `Status: claimed` *before* any work. A ticket is on the frontier when it is `Status: open`, not claimed, and every file in its `Blocked by:` list is `Status: resolved`. Open tickets are not listed here — query the directory. Research output is written to `research/<NN>-<slug>.md` and linked from the ticket's `## Answer`, never pasted in.

- [Evaluate mutation testing as a way to find what coverage cannot see](issues/22-evaluate-mutation-testing.md) — PIT 1.19.0 mutates this Kotlin bytecode usefully (749 mutants, 103 s, 7% mechanical noise; `NON_VOID_METHOD_CALLS` is in PIT's `ALL` group but **not** in `STRONGER`, which is why starting there misses every value-returning call) and the headline gap is real: **test strength 74.6% (534/716 covered mutants) against 95.33% Kover line coverage** on the same compilation. **Verdict: an on-demand `pitestJvm` task, not a gate** — one mutant is 0.14pp at this size, repeat runs flip 0.8%, and it would quadruple a 41 s `check`. Its sharpest result is negative: **none of the three behaviours the humans caught by reading the sibling suites produced a matching survivor**, because mutation testing finds wrong implementations, not *missing* checks (`parseBody` never reads `content-type`, so there is no bytecode to mutate) — it earns its place only where a wrong decode would survive, and it did find the empty-`200`-body cluster (11 survivors) that ticket 21 ports plus 157 malformed-input mutants across `ErrorMapping`/`Client`/`Answers`. **Two of ticket 21's premises were falsified by it** and are corrected there: the trailing-slash base URL and the mixed-case `accept` pair are already pinned. The integration is the fiddly part: a KMP module never applies `JavaPlugin`, so the plugin's own `PitestTask` is registered against the JVM test compilation by hand, and `additionalClasspathFile`'s parent directory plus `runtimeDependencyFiles` each cost a run to discover. **Amended:** `pitestJvm` now excludes `*lambda*` targets — synthetic methods Kotlin inlines lambda bodies into, which no source file contains — taking survivors **139 → 122** and strength 81.1 % → 82.5 %. `avoidCallsTo` and an `*$*` class glob were both tried and reverted, because Kotlin puts `runCatching`/`Intrinsics` calls on the same source line as real logic: the first cost `parseBody` every one of its mutants, the second deleted suspend-function bodies that compile into `Enclosing$1.invokeSuspend`. Two consecutive runs of the identical configuration then disagreed on **6 of 727 mutants (0.8 %)**, in both directions and including a test-strength move of 82.5 % → 83.0 %, which reproduces this ticket's flakiness figure as named error/cancellation paths. Consequence: neither a threshold nor a committed survivor baseline is defensible — the ledger was prototyped and proven line-shift-proof (keyed on PIT's identity tuple, not line numbers, so a 10-line insert elsewhere produced 0 new and 0 stale) and then **deliberately not adopted**, since there is no prior release to baseline against and the ±6 mutant noise floor would make a "no new survivors" gate flaky by construction. arcmutate's Kotlin plugin, the one tool that filters compiler-generated null handling properly, was declined as a paid third-party artefact on a release-time check.
- [Replicate the sibling test cases, and expose the resolved settings](issues/21-replicate-sibling-test-cases.md) — every test name in both sibling suites was mined and diffed against ours; eight cases had no analogue and are now ported, each carrying the sibling test's name in a comment. One candidate was already covered (the trailing-slash base URL `TransportTest` has pinned all along, and the mixed-case candidate narrowed to the protected names nobody had spelled differently) — ticket 22's mutation run caught both false premises. **The mutation delta is this ticket's non-vacuity proof: test strength 74.6% → 81.1%, survivors 185 → 139** (`ErrorMapping` 39→22, `Client` 33→19, `Answers` 20→8), with the equivalent and off-by-one survivors left behind by name and reason. Also landed: the **six resolved settings** on `TypeSafeClient` (`baseUrl`, `defaultModel`, `timeout`, `retry`, `logLevel`, `defaultHeaders` — the effective values, with no accessor for the API key, which stays in the transport), and the **KDoc fence is now compiled**: `generateReadmeSnippets` became `generateDocSnippets`, one regex against a second input, proven by watching a KDoc snippet's `systemOne` → `systemTwo` break `compileTestKotlinJvm`. One divergence found and **deliberately not fixed**: `ErrorMapping.validationEntry` drops an integer `loc` segment (`questions`) where Python stringifies every segment (`questions.0`), and drops only a leading `body` run where Python drops it anywhere — a user-visible error string, so it is recorded rather than changed.
- [Give the on-demand mutation run a trigger, at release time](issues/23-trigger-the-mutation-run.md) — PIT now has a trigger instead of a habit: `docs/releasing.md` is the pre-tag procedure (`check` green on `main` → `pitestJvm` → the human prerequisites, linked to ticket 15 rather than restated), and `publish.yml` runs the same task on the tag push with `continue-on-error: true`, so the strength and survivor count land in the release run's log and a measurement can never fail a release. `check` is unchanged and `pitestJvm` stays outside it; the README's "on demand" subsection now points at the doc. All eight `generatePomFileFor*Publication` POMs still contain zero references to `pitest` or `arcmutate`. **The parent corrected its baseline**: the worktree was cut from `ece128a`, before ticket 21's port merged, so its recorded 762 mutants / 183 survivors / 74.9 % measured the pre-port tree (185 survivors is what ticket 21 started from) — `docs/releasing.md` now carries the runs at `39eaccb` on the tree as it stands (727 mutants, 118–122 survivors, **test strength 82.5–83.0 %**), keeping the stale figure only as provenance with the reason it is not comparable. ## Out of scope

<!-- beyond the 0.1.0 destination; closed, never graduates -->

- **JS and Wasm targets.** The build is KMP-shaped from line one specifically so this is additive later, but a `fetch` engine and a second async model are a v0.2 concern.
- **A blocking / `runBlocking` JVM facade shipped by us.** `runBlocking` is one line for a caller who wants it; shipping it is a footgun on Android's main thread.
- **KSP or Gradle-plugin codegen for typed questions.** The typed-key API gets the same safety without a compiler plugin.
- **A published documentation site, and a `samples/` Gradle module.** README + Dokka + `explicitApi()`-enforced KDoc; the README *is* the sample.
- **`extra_body`, a pluggable `Logger` abstraction, and per-call extra headers.** Deferred in the design brief; logging stays on/off only.
- **Python's whole-retry-budget timeout.** Per-attempt timeout plus the `maxRetryAfter` cap, nothing more, until someone asks.
- **Upstream `ai.typesafe:*` coordinates.** We ship our own group id; a handover is a Maven-only change.
